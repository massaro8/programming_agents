# Infrastructure engineering contract

Inputs: versioned environment and parameter declarations, local templates, explicit branch and caller-provided account/role references. Outputs: offline validation diagnostics and a resolved environment context. Reference resolution never contacts AWS or resolves secret values. Unknown branches, missing references, wrong accounts and wrong regions fail closed; production has no fallback.

Parameter declarations carry name, type, required, source, environment and sensitive fields. Sensitive inputs declare Secrets Manager or SSM SecureString dynamic references only; resolved secret values and sensitive defaults are forbidden. Remote resolution is future deployment work. Commit only nonsensitive defaults and reference identifiers.

Inspection is separate from validation. Use the canonical aws-infrastructure-inspection skill. Name an environment, profile, region, stack and expected read-only role, authorize inspection explicitly, and compare STS identity before accessing resources. IAM policy on that role is the actual read-only boundary; an ARN alone cannot establish its permissions. No profile configuration, role creation, deployment, template retrieval or secret retrieval is allowed. Metadata is bounded and outputs require an explicit nonsensitive allowlist. Missing tools, credentials or permissions fall back to local evidence.

For module references, Ref/GetAtt preserve local dependencies; nested-stack outputs couple lifecycle. Export/ImportValue operates within an account and region and prevents modifying exports while imported. [Fn::GetStackOutput](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/intrinsic-function-reference-getstackoutput.html) supports cross-account/cross-region outputs using explicit region and role configuration; review freshness, authorization and lifecycle separately. Explicit parameter contracts offer portable orchestration but require ownership of propagation. [AWS outputs reference](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/outputs-section-structure.html).

GitHub and Bitbucket pipelines run the same local project verification entry point. A future deployment workflow must separately configure narrow OIDC trust, branch/environment restrictions and provider-managed approval controls. It must never reuse inspection approval as deployment approval. [Bitbucket OIDC](https://support.atlassian.com/bitbucket-cloud/docs/deploy-on-aws-using-bitbucket-pipelines-openid-connect/) and [deployment permissions](https://support.atlassian.com/bitbucket-cloud/docs/set-custom-deployment-permissions-for-your-environments/). The checked-in validation pipeline has no AWS credentials or deployment commands.
